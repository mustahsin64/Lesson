Functional Programming • Lecture 01

Why Functional Programming Matters

Applying Functional Programming Principles

1. Introduction

Functional programming (FP) is a programming paradigm that emphasizes functions, explicit data flow, immutability, and minimizing side effects.

The goal is not necessarily to write an entire application in a purely functional style.

Instead, the important goal is to learn functional programming deeply enough that you can apply its principles to other programming paradigms, including Object-Oriented Programming (OOP).

Given the same input, a function should consistently produce the same output.

2. Two Ways of Thinking About Code

Imperative / Mutable approach

var price = 100
var discount = 20

price = price - discount

Here, price changes. Initially it is 100, then it becomes 80. The program relies on the current state of the variable.

Functional approach

func finalPrice(price: Int, discount: Int) -> Int {
    return price - discount
}

let result = finalPrice(price: 100, discount: 20)

The result is 80. The function doesn't modify external state. It simply takes inputs and produces an output.

Input ↓ Function ↓ Output

3. The Problem With Hidden State

var discount = 20

func finalPrice(price: Int) -> Int {
    return price - discount
}

At first, finalPrice(price: 100) produces 80.

But if another part of the application executes:

discount = 50

the same function call now produces 50.

The function itself hasn't changed. However, its result changed because it depends on an external mutable variable.

Key idea: The function appears to need only price, but actually also depends on discount. This is a hidden dependency.

4. Why Mutable State Causes Bugs

Imagine a real application containing:

User Cart Product Payment Discount Shipping Order

Suppose the cart contains mutable properties:

class Cart {
    var total: Double = 0
    var discount: Double = 0
    var shipping: Double = 0
}

Different parts of the application might modify them:

cart.total = 1000
cart.discount = 100
cart.shipping = 60

cart.total = cart.total - cart.discount

If the expected result is 960 but the application produces something else, you may need to investigate:

  • Who changed total?
  • Who changed discount?
  • When did they change it?
  • In what order?
  • Was something changed twice?
  • Did another component modify the cart?
  • Was stale state used?

The problem isn't necessarily one bad calculation. The problem is that many parts of the application can change shared state.

5. Functional Programming Changes the Design

Instead of having many objects modifying shared state, we can move toward small functions that transform explicit inputs into outputs.

func calculateTotal(
    subtotal: Double,
    discount: Double,
    shipping: Double
) -> Double {
    subtotal - discount + shipping
}
calculateTotal(
    subtotal: 1000,
    discount: 100,
    shipping: 60
)

// 960

The function doesn't need to modify a Cart. It simply calculates a value from the information given to it.

6. Command vs Calculation

Command

cart.total = cart.total - cart.discount

This essentially says:

Change the object's state.

Calculation

let newTotal = calculateTotal(
    subtotal: cart.total,
    discount: cart.discount,
    shipping: cart.shipping
)

This says:

Given these inputs, calculate a result.

The original values aren't modified by the function. This makes the calculation easier to reason about and test.

7. Why Pure Calculations Are Easier to Understand

let total = calculateTotal(
    subtotal: 1000,
    discount: 100,
    shipping: 60
)

To understand the result, you only need to understand calculateTotal().

1000 - 100 + 60 ↓ 960

You don't need to investigate the entire application. This is one of the major benefits of functional programming.

8. Referential Transparency

A key concept in functional programming is referential transparency.

For now, use this simplified definition:

A function is referentially transparent when it can consistently be replaced by its result without changing the program's behavior.
func add(_ a: Int, _ b: Int) -> Int {
    a + b
}

add(10, 20)
// 30

Because it always produces 30, this:

let result = add(10, 20)

is effectively equivalent to:

let result = 30

9. Mutable State Breaks This Property

var taxRate = 0.15

func calculateTax(price: Double) -> Double {
    return price * taxRate
}

Initially, calculateTax(price: 100) returns 15.

But after:

taxRate = 0.20

the exact same function call returns 20.

The input appears to be the same, but the result changed because the function secretly depends on taxRate outside its parameters.

10. Make Dependencies Explicit

func calculateTax(
    price: Double,
    taxRate: Double
) -> Double {
    price * taxRate
}

Now:

calculateTax(
    price: 100,
    taxRate: 0.15
)

// 15

and:

calculateTax(
    price: 100,
    taxRate: 0.20
)

// 20

The dependency is now explicit.

Central principle: Prefer explicit dependencies over hidden dependencies.

11. Functional Programming Does Not Mean "Never Change Anything"

Functional programming does not mean:

Never use variables.

Instead:

Avoid unnecessary mutable state and isolate unavoidable side effects.

Real applications inevitably interact with the outside world. For example, an iOS application might do:

User taps button ↓ Network request ↓ Server responds ↓ Data changes ↓ UI updates

These interactions involve state and side effects. The goal isn't to eliminate them completely. Instead, we try to keep them controlled and separate from pure logic.

12. The Bigger Design Idea

Move away from:

Many objects ↓ Many mutable properties ↓ Many methods modifying them ↓ Hidden dependencies ↓ Hard-to-reproduce bugs

Move toward:

Data ↓ Small Function ↓ New Data ↓ Small Function ↓ Result

This can provide:

  • Fewer hidden dependencies
  • Easier testing
  • Easier debugging
  • Easier reasoning
  • Better separation of responsibilities
  • Greater referential transparency
  • Fewer accidental interactions between components

13. A Functional Programmer's Mental Model

Question 1 — What does this function need to know?

Ideally, the answer should be:

Its parameters

rather than global variables, singletons, mutable properties, external objects, or hidden state.

Question 2 — Does this function change something outside itself?

If yes, it may have a side effect. We will study side effects in a later lecture.

Question 3 — If I give it the same inputs twice, will I definitely get the same result?

If yes, you're moving toward functional programming.

14. Mental Exercise

var taxRate = 0.15

func calculateTax(price: Double) -> Double {
    return price * taxRate
}

Question: Is this function behaving like a good functional function?

The function receives price, but its result also depends on taxRate, which exists outside the function.

Therefore, calculateTax(100) could produce 15 or 20 depending on the current state of taxRate.

A more functional design is:

func calculateTax(
    price: Double,
    taxRate: Double
) -> Double {
    price * taxRate
}

Now the function's dependency is explicit.

15. Core Takeaways

1. Mutable state creates hidden dependencies.
External mutable state makes code harder to reason about.
2. Prefer explicit inputs.
Pass dependencies into functions rather than having functions secretly obtain them.
3. Prefer calculations over unnecessary mutations.
When appropriate, calculate and return new values instead of changing existing state.
4. Functional programming is a way of thinking.
You don't have to abandon OOP. Make your OOP code more functional by increasing explicit data flow and reducing unnecessary mutation.

Final Mental Model

FUNCTIONAL THINKING Data ↓ Explicit Inputs ↓ Function ↓ Output

The more your code can follow this model, the easier it generally becomes to understand, test, debug, and maintain.
